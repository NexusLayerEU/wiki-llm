Now here's the architecture for WikiForge: System Overview — 3 layers: 1. Ingestion Layer — A file watcher (inotify/polling) monitors each project's source directory. When files are added or modified, they enter a processing queue. Parsers extract raw content: python-docx for .doc/.docx, openpyxl for .xlsx, PyMuPDF for PDFs, and raw read for .md. A delta-detection system (hash-based) avoids reprocessing unchanged files. 2. LLM Processing Pipeline — 7 stages run per file: Ingest → Parse → LLM Extract (structure, headings, key entities) → Classify (auto-categorize into wiki sections) → Generate (produce clean wiki markdown) → Cross-link (find relationships between pages using embeddings similarity) → Publish (write to output directory + update the served wiki). Each stage is a queue-based job with status tracking, token counting, and retry logic. 3. Serving Layer — A FastAPI backend serves both the Web UI and the Wiki API. The wiki is served as static markdown rendered to HTML, with a full REST API for agents. The /agent/query endpoint does RAG (retrieval-augmented generation) over the wiki content for natural language queries. Key design decisions: Each project is self-contained: source dir, output dir, its own wiki namespace, independent processing pipeline Auto-update works via filesystem watching — modify a file, and only that file gets reprocessed (delta mode), then the affected wiki pages regenerate The API is agent-first: OpenAPI spec at /agent/openapi.json, semantic search, RAG query endpoint, and structured JSON responses — ready for MCP or tool-use integration Monitoring tracks LLM token usage, processing latency, success rates, and file watcher health per project Suggested tech stack: Python + FastAPI backend, Celery/Redis for job queues, SQLite per project for metadata, Anthropic SDK for LLM calls, and the React/HTML frontend you see in the prototype. System Architecture

The OSPD platform consists of a Kubernetes-orchestrated microservices architecture deployed across Oracle Cloud Infrastructure (OCI) ARM instances. Traffic is managed through nginx reverse proxies with load balancing configured for portal2.ospd.gr.

Key Components

The deployment stack includes Spring Boot applications exposing REST APIs, a MariaDB Galera cluster for high availability, Wazuh SIEM for security monitoring (estimated at 150 servers, sizing calculated for EPS/LPS requirements), and WireGuard VPN tunnels for secure inter-node communication.

Monitoring & Observability

Metrics are collected via Micrometer/Prometheus integration on Spring Boot services, with Portainer providing container management UI. The transcription service processes Greek-language audio through dedicated API endpoints.
